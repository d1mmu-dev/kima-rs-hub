## Review Focus

1. **Never a 500 for someone else's trouble.** Upstream maps Apple/feed/audio failures to 404 (`missing`: guard refusal or a 4xx other than 429), 502 (`down`: 429, 5xx, timeout, unreachable, garbled reply) and, for subscribe, 422 (a page that is not a feed) (`utils/upstream.ts:24-48` [V], `podcasts.ts:171-186,808-825,1075-1083` [V]). kima-rs maps `kima_net::Outcome` the same way (Task 5 `Upstream::classify`); every route test file has a "host down / host 404 / garbled" case.
2. **Public addresses only, at every hop.** A feed, an enclosure, a cover and every redirect of each are fetched only from public unicast addresses, with the connection pinned to the checked addresses (`kima-net` image rule, `ssrf.rs`, `images.rs:1-5` [V]). Upstream's `guardedAxios` does the same (`utils/ssrf.ts` [C]). Tests redirect a replay to a private address and expect the "not available" 404, not a fetch.
3. **Streaming proxy.** No buffering of whole episodes; a client abort cancels the upstream body; one range passes through, several ranges → whole file 200, CDN refusing a range → retry without (`podcasts.ts:1045-1059` [V]); 416 mirrored with `Content-Range`; `Content-Length` is the host's, never the feed's `enclosure length` (`podcasts.ts:1024-1027` [V]).
4. **AI label correctness.** Missing tag = `unknown`; label and `explicit` are separate columns and separate wire keys and no code path derives one from the other (test `ai_label_and_explicit_are_independent`); hiding is applied server-side to every list (REST and Subsonic) and is never silent (`X-Kima-Ai-Hidden` header, Task 8).
5. **Concurrency.** Two follows of one new show store one show (upstream P2002 path `podcasts.ts:789-797` [V] → `ON CONFLICT`); manual and scheduled refreshes race on `(podcast_id, guid)` (`podcasts.ts:1248-1254` [V] → `ON CONFLICT DO NOTHING`); one episode is never downloaded twice at once (job key dedupe); a cached file is served only when its record matches (`podcastDownload.ts:25-59` [V]).

## AI-content filter: specification (written here; `references/podcast-ai-filter.md` does not exist)

This section is the spec the owner rule points at. It is **kima-rs-only behaviour** (upstream v1.12.3 has no AI concept in podcasts: `git grep -n -i "ai-content\|aiLabel" c7527577 -- backend frontend` is empty [V]) and is recorded as D-200 (decision) and D-207/D-208 (wire/Subsonic).

### S1. States and sources

- **Label** ∈ `ai` | `human` | `unknown`. **Label source** ∈ `feed-episode` | `feed-show` | `admin` | `null` (null only with `unknown`).
- `ai`: the effective signal says AI-generated content. `human`: the effective signal says no AI-generated content (a publisher's explicit `false` or an admin's confirmation; the source tells which, and the UI says "declared by publisher" vs "confirmed by admin" — Q1b). `unknown`: no signal. **No signal never becomes `human`.**
- **Independence from suitability:** `explicit` (from `itunes:explicit`, upstream `rss-parser.ts:285-289` [V]) is stored and sent unchanged; it is not read when resolving the AI label and the AI label is not read when deciding `explicit`. There is no "family"/kids filter in upstream; none is added.

### S2. Resolution (per recommended Option A + F, D-200)

Stored inputs: `podcasts.ai_feed` (channel-level tag: `true`/`false`/NULL), `podcasts.ai_override` (`'ai'`/`'human'`/NULL, admin), `podcast_episodes.ai_feed` (item-level tag: `true`/`false`/NULL), `podcast_episodes.ai_override` (`'ai'`/`'human'`/NULL, admin; owner decision 2026-11-13: the override exists per show **and** per episode).

- **Show label** = `ai_override` if set (source `admin`) → else channel tag (source `feed-show`) → else `unknown`.
- **Episode label** = the episode's admin override if set (source `admin`) → else item tag if present (source `feed-episode`) → else the show label with its source (`admin` or `feed-show`) → else `unknown`. An item tag beats an admin show override: it is the publisher's statement about that episode (owner: "the episode label takes precedence over the show label"); an admin episode override beats both, so an admin can correct a wrong item tag (Castos/Spreaker emit item tags exactly for the "AI bonus episode on a human show" case [V, see research R2–R3]).
- **Parsing:** `<podcast:txt purpose="ai-content">VALUE</podcast:txt>` in the Podcasting 2.0 namespace (`https://podcastindex.org/namespace/1.0`; matched by namespace URI, not prefix), at `<channel>` and `<item>` level. `purpose` compared trimmed and ASCII-case-insensitively; `VALUE` trimmed, `true`/`false` case-insensitively; anything else (empty, `yes`, `maybe`) is **no signal** for that tag. Several `ai-content` tags at one level: any `true` → `true` (a contradictory feed is treated as AI; the pill shows it on request), else `false` if any `false`, else no signal.
- **Refresh:** on every non-304 refresh the channel tag and **every stored episode's** item tag are re-read from the feed (D-206: upstream leaves existing episodes untouched, `podcasts.ts:1248-1254` [V]; a publisher may add a disclosure later). An episode no longer in the feed keeps its last tag.

### S3. Where labels appear (wire, additive; upstream clients ignore unknown keys)

- Every podcast object (list, detail, preview, discovery items, search results, listening/next rows' `podcast`) gains `"aiLabel"` and `"aiLabelSource"`; every episode object gains the same pair for the episode.
- **Discovery items** (Apple charts, for-you, similar, `/search/discover`) carry no feed: their label is taken from a stored show with that `itunes_id`, else from `podcast_feed_labels` (channel tag remembered when a preview read the feed, Task 14), else `unknown`. kima-rs does **not** crawl chart feeds to label them (200 feeds per chart against strangers' hosts; Q1d). So charts are mostly `unknown` and stay visible: honest, not "human".

### S4. Hiding (default) and the switch

- Per-user setting `user_settings.podcast_ai_filter` ∈ `hide` (default) | `show`, exposed in `GET/POST /api/settings` as `"podcastAiContent": "hide" | "show"` (validation 400 `{"error":"podcastAiContent must be hide or show"}`).
- Per-request override on every REST list route: `?ai=hide|show` (other value → 400 `{"error":"ai must be hide or show"}`); absent → the user's setting.
- With `hide`: lists drop shows whose show label is `ai` and episodes whose episode label is `ai`. Lists = `GET /podcasts`, `/podcasts/listening`, `/podcasts/:id` (its episode page), `/podcasts/:id/episodes`, `/podcasts/charts`, `/discover/*`, `/for-you`, `/:id/similar`, `/preview/:itunesId/similar`, `/search` podcasts+episodes groups, `/search/discover` podcasts, `/library/recently-listened` podcast items, `.../next` (skips AI episodes like finished ones). **Not filtered:** direct reads by id (`GET /podcasts/:id` still answers for an AI show, labelled; `/preview/:itunesId` answers an AI show too, labelled with its channel tag, and its `previewEpisodes` are not labelled per item before following — D-207), stream/progress/cover routes, `/stats` (history is history).
- **Never silent:** a filtered response carries `X-Kima-Ai-Hidden: <n>` (number of items the filter removed from the candidate set before paging; `0` when nothing was removed; header absent with `ai=show`). Paged totals (`episodeTotal`, `total`) count visible items only. Lists filter in the query, before their limit (D-207/D-208). [2026-11-13: the episode page, show detail and `/podcasts/listening` also carry the count in the body as `aiHidden`, because kima-web cannot read response headers (D-207).]
- **Subsonic** (`getPodcasts`, `getNewestPodcasts`, channel episodes) uses the user's persisted setting (no per-request switch exists in the protocol); `getPodcastEpisode` by id is not filtered (D-208).
- **UI (kima-web, Task 22–23):** badges "AI", "Human" (tooltip: declared by publisher / confirmed by admin), "Unlabelled"; a separate "E" explicit badge [2026-11-13: not built — upstream's wire shapes carry no `explicit` key; recorded in D-207]. A pill on the podcasts home, show page and search tab: "N AI hidden · Show" ↔ "Showing AI · Hide" (sets `?ai=` for the view); Settings has the persistent switch. Admins get "Mark as AI / Confirm human / Clear" on the show page.
- **Admin override route** (kima-only): `PUT /api/podcasts/:id/ai-label` body `{"label":"ai"|"human"|null}` → 200 `{"aiLabel":…, "aiLabelSource":…}` (the show\'s resolved label), and `PUT /api/podcasts/:podcastId/episodes/:episodeId/ai-label` with the same body for one episode (200 with the episode\'s resolved label; 404 when the episode is not one of that show\'s); 403 for non-admins (project body), 404 unknown show, 400 bad body `{"error":"label must be ai, human or null"}`.

## AI-content detection source: research and options (decision → D-200 in Task 0)

Retrieved 2026-11-12 via web search/extract; quotes are from the pages named.

**R1. Podcasting 2.0 `podcast:txt` purpose `ai-content` (namespace documentation).** The `<podcast:txt>` tag (parent `<channel>` or `<item>`, multiple allowed, `purpose` attribute ≤ 128 chars) lists `ai-content` among known purposes: "The node value is expected to contain a boolean (`true` or `false`) indicating whether AI-generated content was used in the production of the podcast or episode. This works exactly like `itunes:explicit`. When used at the `<item>` level, it applies to that specific episode. When used at the `<channel>` level, it applies to the podcast as a whole. Some prefer to automatically set the `<channel>` level value to true when at least one `<item>` in the feed contains a true value." — https://podcasting2.org/docs/podcast-namespace/tags/txt. Added by PR #757 "Add ai-content as a known purpose for the podcast:txt tag" (opened 2026-03-05) — https://github.com/Podcastindex-org/podcast-namespace/pull/757. Guidance link: https://shouldidisclose.ai/ ("Disclose when AI is doing the creative work your listeners came for", https://shouldidisclose.ai/about.html).

**R2. Hosts emitting it.** Castos: one answer per show plus optional per-episode answers, written as `<podcast:txt purpose="ai-content">true</podcast:txt>`; "Not answered yet" → **no tag**; a show is also marked AI if any episode says Yes; "As of October 2026, we're not aware of any major podcast app, including Apple Podcasts, Spotify, YouTube, Pocket Casts and Overcast, that shows listeners a label based on it yet." — https://support.castos.com/article/502-ai-content-disclosure. Spreaker: item-level tag for each flagged episode and the same tag at channel level if at least one episode is flagged; non-disclosure "may result in the account being suspended or closed" — https://help.spreaker.com/en/articles/12458456-ai-generated-content-in-your-podcast-and-episode-descriptions. RSS.com: per-episode Yes/No, "If any episode answers Yes, the show carries the AI label too. We add the label to your RSS feed", and "Apple Podcasts does not read that label" — https://help.rss.com/en/support/solutions/articles/44002773969-guidelines-for-labeling-ai-generated-content; tag lives in `podcast:txt` — https://rss.com/blog/ai-disclosure-in-podcasting-what-it-is-why-it-matters-and-how-to-do-it/. Apps: Truefans reads `podcast:txt purpose=ai-content` (comment in https://github.com/Podcastindex-org/podcast-namespace/discussions/731) [C].

**R3. Consequence for "human".** Hosts write `false` when the creator answered No (Castos "No" = AI only a production tool; RSS.com "No"), and write **nothing** when unanswered (Castos table). So an explicit `false` is a publisher declaration; absence says nothing — matching owner rule 3.

**R4. Apple.** Content guideline 1.11: creators using AI to generate audio "must prominently disclose this to audiences in the content and metadata for each episode and show" — https://podcasters.apple.com/support/891-content-and-subscription-guidelines — but Apple names no metadata field (Castos and RSS.com above). **R5. **R6. Unadopted proposals.** `<podcast:ai>` (https://github.com/Podcastindex-org/podcast-namespace/discussions/735, labelled duplicate/proposal), `<podcast:disclosure>` (#669, https://github.com/Podcastindex-org/podcast-namespace/discussions/669), synthetic voices via `podcast:person` (#731), "Generative AI Disclosures" (#663, https://github.com/Podcastindex-org/podcast-namespace/discussions/663).
