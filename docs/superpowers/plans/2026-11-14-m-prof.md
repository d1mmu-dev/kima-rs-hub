# M-PROF (profiles per account, Netflix-style) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** an account (a `users` row: username, password, role) holds up to **5 profiles**: exactly one `main`, any number of `kids`/`standard` profiles within the limit. Everything a user owns today (settings, playlists and hidden playlists, plays and the play-history audit, stars, ratings, playback state, Subsonic bookmarks, podcast follows/progress/downloads and the AI-content setting, app tokens) becomes owned by a **profile**. The library and server settings stay shared per server; admin rights stay with the account's main profile. `kima-web` gets a "Who's listening?" picker after login, a profile switcher in the header and profile management in Settings; switching profile needs no re-login. Existing data lands in each account's main profile; existing clients (upstream-shaped `/api`, Subsonic apps, the legacy `frontend/` comparison reference) keep working unchanged against the main profile.

**Architecture:** one migration (`0060_profiles.sql`) adds `profiles` and re-keys the 13 per-user tables from `user_id → users(id)` to `profile_id → profiles(id)`. **The main profile's id is the account's id** (`profiles.id = profiles.user_id` exactly for `kind = 'main'`, enforced by a CHECK), so the upgrade rewrites no data row, every existing JWT, Subsonic session, queued job payload and client-cached id keeps meaning "this account's main profile", and the migration is a rename plus FK swap in one transaction. Rust gets newtypes `AccountId`/`ProfileId` (kima-core) so the compiler, not the tests, finds every place that must choose between the two. The JWT gains an optional `profileId` claim (absent = main). Subsonic app tokens (`api_keys`) belong to a profile; token auth signs into the token's profile, password auth into the main profile.

**Tech Stack:** unchanged (Rust 2024, axum 0.8, sqlx 0.8, tokio, Postgres 17, vertigo 0.13.4 for `kima-web`). Test-only: `axum_test`, `#[sqlx::test]`, `tools/verify-kima-web-e2e.mjs`.

**Specs / parents:** roadmap row M-PROF (`docs/superpowers/plans/2026-10-16-kima-rs-roadmap.md:30`, owner decisions 2026-11-13); parent spec `docs/superpowers/specs/2026-10-16-kima-rust-design.md` (§5 auth); M9 spec §12 (kima-web token in its own `localStorage` key); divergence log `docs/DIVERGENCES.md` (highest row on this base: D-239).

## Owner decisions (binding, 2026-11-13; do not re-ask)

1. Netflix-style profiles inside an account: **main + kids + up to 3 more, max 5 per account.**
2. **Each profile owns everything a user owns today**: settings, playlists, plays/stats (incl. play audit), stars/ratings, playback state, podcast follows/progress/AI-content setting, Subsonic app tokens/bookmarks; later vibe/mixes/radio.
3. **Library is shared per server; admin rights stay with the account's main profile.**
4. **"Who's listening?" picker in kima-web; switch profile without re-login.**
5. **Kids = a profile type with NO content filters for now** (no hiding of explicit or untagged music); filters are designed later, once AI labelling is in use. The type must allow adding filters later **without a data migration**.
6. **No PIN now**; the switch flow must leave room for an optional PIN on the main profile later (~0.5–1 day then).
7. **Subsonic app tokens per profile** (a phone app logs into a specific profile).
8. **Existing data of every account goes to its main profile** (roadmap row: "existing data migrated into each account's main profile").
9. Estimate given to the owner: **2–3 weeks**. Sequencing: right after M6a, before M5/M5b/M7/M6b add more per-user tables.

Consequence of 2 + 7: in kima-rs the "API keys" of `/api/api-keys` **are** the Subsonic app tokens (`crates/kima-api/src/routes/api_keys.rs:1` [V], `kima-subsonic/src/auth.rs` `apiKey`/`t`+`s`/token-as-`p`), so "API keys per account or per profile" is already decided: **per profile**. Not an open question.

## Review Focus

1. **Main-profile masking** (Global Constraints). Reviewers check that each changed call site picks `profile` or `account` per Appendix A, and that each route's isolation test logs in as a non-main profile. A green suite run only as main proves nothing about this milestone.
2. **Auth lookup is one query and binds profile to account.** `authenticate` must load the profile **joined to the account named in the token** (`WHERE p.id = $profile AND p.user_id = $user`); a token whose `profileId` names a profile of another account (forged with a leaked secret, or a stale id) is 401, never "that other profile". A deleted profile is 401 on the next request, no cache.
3. **Subsonic token+salt stays constant-time.** `ts_rounds` keeps exactly `TS_ROUNDS = 50` rounds over the **account's** tokens (all profiles), so the cap `MAX_PER_USER = 50` stays per account; the match picks the profile. `u` stays the account username.
4. **Migration is one transaction, rewrites no row, and every FK ends up on `profiles` with `ON DELETE CASCADE`.** The upgrade test checks `pg_constraint` (no FK from the 13 tables to `users` remains) and compares a full ordered dump of the 13 tables before/after (only the column name differs).
5. **Admin = role admin AND main profile**, on `/api` (`AdminUser`) and Subsonic (`require_admin`). A kids/standard profile of an admin account is 403 / Subsonic error 50 on every admin route.
6. **Events and SSE are per profile**; account-wide revocation (password change, account delete) still reaches every profile's streams.
7. **Profile delete** cascades exactly that profile's rows; siblings and other accounts untouched; main cannot be deleted except with its account.

## Design decisions (with justification)

### (a) Schema

```sql
-- 0060_profiles.sql (one file = one transaction under sqlx)
CREATE TABLE profiles (
    id         uuid PRIMARY KEY,
    user_id    uuid NOT NULL REFERENCES users (id) ON DELETE CASCADE,
    name       text NOT NULL CHECK (name = btrim(name) AND length(name) BETWEEN 1 AND 50),
    kind       text NOT NULL CHECK (kind IN ('main', 'kids', 'standard')),
    avatar     text CHECK (avatar ~ '^[a-z0-9-]{1,32}$'),   -- preset key (Q1); NULL = initial on colour from id
    created_at timestamptz NOT NULL DEFAULT now(),
    -- The main profile IS the account: same id. Gives "exactly one main per account" via the PK.
    CHECK ((kind = 'main') = (id = user_id))
);
CREATE UNIQUE INDEX profiles_user_name_key ON profiles (user_id, lower(name));   -- Q5
CREATE INDEX profiles_user_idx ON profiles (user_id);

-- Backfill: one main profile per existing account, named after the account.
INSERT INTO profiles (id, user_id, name, kind, created_at)
SELECT id, id, username, 'main', created_at FROM users;

-- Every new account gets its main profile in the same statement (register, create-user, Subsonic createUser,
-- test fixtures that insert users by SQL: no code path can forget it).
CREATE FUNCTION users_main_profile() RETURNS trigger …  INSERT INTO profiles VALUES (NEW.id, NEW.id, NEW.username, 'main', NULL, NEW.created_at);
CREATE TRIGGER users_main_profile AFTER INSERT ON users FOR EACH ROW EXECUTE FUNCTION users_main_profile();

-- At most 5 per account, race-free: lock the account row, then count (same lock api_keys::create takes).
CREATE FUNCTION profiles_limit() RETURNS trigger … PERFORM 1 FROM users WHERE id = NEW.user_id FOR UPDATE;
    IF (SELECT count(*) FROM profiles WHERE user_id = NEW.user_id) >= 5 THEN
        RAISE EXCEPTION 'profile limit reached' USING ERRCODE = 'P0001', HINT = 'kima:profile_limit';
CREATE TRIGGER profiles_limit BEFORE INSERT ON profiles …

-- The main profile goes only with its account.
CREATE FUNCTION profiles_keep_main() RETURNS trigger … IF OLD.kind = 'main' AND EXISTS (SELECT 1 FROM users WHERE id = OLD.user_id)
    THEN RAISE EXCEPTION 'main profile cannot be deleted' USING HINT = 'kima:profile_main';
CREATE TRIGGER profiles_keep_main BEFORE DELETE ON profiles …

-- Re-key, ×13 (FK names are the Postgres defaults <table>_user_id_fkey; Task 1 asserts them first):
ALTER TABLE plays RENAME COLUMN user_id TO profile_id;
ALTER TABLE plays DROP CONSTRAINT plays_user_id_fkey,
    ADD CONSTRAINT plays_profile_id_fkey FOREIGN KEY (profile_id) REFERENCES profiles (id) ON DELETE CASCADE;
```

**Why main id = account id (chosen) rather than the alternatives:**

| Option | Upgrade | Old JWTs / Subsonic / queued jobs | Risk |
|---|---|---|---|
| **C. rename `user_id → profile_id`, main profile id = account id (chosen)** | no row rewritten; rename + FK swap (FK validation scans each table once) | valid as-is: every stored user id already is the main profile id | masks account/profile mix-ups on main → newtypes, non-main test matrix, grep gate |
| B. rename + fresh main-profile ids, backfill `UPDATE … SET profile_id = main.id` | rewrites every row of 13 tables (plays is the big one) | need a mapping step in auth, Subsonic and the job reader | larger lock time; more code paths |
| A. add `profile_id`, keep `user_id` | backfill + dual columns | as C | two sources of truth, every unique key and query doubles; drift bugs |

Rename (not keep the name `user_id`) so that every static `sqlx::query!` touching these tables fails `cargo sqlx prepare` until reviewed, and the grep gate can find runtime SQL.

**Limit and uniqueness in the DB, not only in the app:** the limit trigger and the unique index make the rules hold for every writer, including concurrent requests; the app maps `HINT kima:profile_limit` → 409 `"Profile limit reached"`, unique violation → 400 `"Profile name already taken"`, `kima:profile_main` → 400 `"Cannot delete the main profile"`.

**Kids filters later without a data migration:** `kind` is the only stored policy input. Task 2 adds `kima_core::profile::ContentPolicy::for_kind(kind)` which today returns `Unrestricted` for all kinds (owner decision 5), carried in `AuthUser`. A later filter milestone either derives everything from `kind` (no schema change) or adds a nullable `content_policy jsonb` column whose `NULL` means "the kind's default" (`ADD COLUMN … NULL` rewrites no data). No profile row ever needs migrating. The AI-content podcast switch (`user_settings.podcast_ai_filter`) is already per profile through the re-key; kids default stays `hide` like everyone (D-246).

**Reversibility:** production rollback = restore the `pg_dump -Fc` taken before the upgrade (the redeploy recipe already takes one). In addition, `crates/kima-db/tests/sql/0060_profiles_down.sql` (test asset, not a migration) reverses the schema when only main profiles hold data: it `RAISE`s if any non-main profile owns a row (unless run with `SET kima.drop_profiles = 'on'`), renames columns back, re-points FKs to `users`, drops triggers/functions/table and deletes the `_sqlx_migrations` row 60. Task 1's test proves up → down returns a schema identical (`pg_dump --schema-only` diff) to 0039's and the data unchanged.

### (b) Auth

- `Claims` gains `#[serde(rename = "profileId", default, skip_serializing_if = "Option::is_none")] profile_id: Option<Uuid>`. Absent → main (`profile = user_id`): every token issued before M-PROF keeps working as the main profile. All three issuers take a `ProfileId`; refresh and stream tokens carry it too (a stream token's `playbackQuality` and podcast cache enqueue are per profile).
- `AuthUser` becomes `{ account: AccountId, profile: ProfileId, profile_kind: ProfileKind, username, role, token_version }`; `id` is removed so every use is revisited by the compiler. `authenticate` runs **one** query (`profiles p JOIN users u ON u.id = p.user_id WHERE p.id = $1 AND u.id = $2`) and checks `token_version`. Unknown/foreign/deleted profile → `None` → 401.
- `AdminUser` = `role == admin && profile_kind == Main`, else 403 `"Admin access required"` (same text).
- **Switch:** `POST /api/profiles/{id}/switch`, body `{ "pin"?: string }` (accepted and ignored until the PIN follow-up; no other field). Needs any valid access token of the same account. Answers `{ token, refreshToken, profile }`. Another account's profile id or a malformed id → 404 `"Profile not found"` (no existence leak). The PIN follow-up only adds: `profiles.pin_hash` (nullable, migration 0061), a check in this one handler when switching **into** a profile with a PIN, and the limiter keyed by (account, profile). No other route issues a token for a non-main profile, so the switch is the single choke point.
- **Login/refresh/register** issue main-profile tokens exactly as today (plus the additive `profile` key); kima-web then shows the picker. Refresh keeps the token's profile; refresh for a deleted profile → 401 `"Profile not found"` (the client signs in again).
- **Logout** stays stateless (`{"message": "Logged out"}`); kima-web clears its keys. **Change password** is main-profile only (403 `"Only the main profile can change the password"`, D-241), bumps the account's `token_version` → every profile's JWTs die, and keeps revoking all the account's app tokens (all profiles), as today.
- **Profile management** (create/rename/change kind/avatar/delete): main profile only (Q3). Listing and switching: any profile of the account.

### (c) Subsonic

- `api_keys.profile_id`: a token belongs to one profile. `find_by_hash` returns `(key_id, account, profile)`; `user_with_secrets(u)` returns the account and the secrets of **all its profiles' tokens** (one query, unchanged timing shape, at most 50 per account); `ts_rounds` keeps 50 rounds; the matched key id resolves the profile. `u` must still equal the account username (case-insensitive) for every method.
- Password auth (`p=` plain/`enc:`) signs into the **main** profile (Q7: no `user@profile` syntax). Old tokens (all created before M-PROF) belong to main after the re-key.
- `require_admin` = admin role **and** main profile. `require_password_auth` unchanged (D-098 still holds).
- Playlist `owner` (`getPlaylists`/`getPlaylist`): the caller's `u` for playlists of the caller's profile (clients compare `owner` with their username to decide editability), the account username for another account's main profile, `username (Profile name)` for another non-main profile (D-244). `getNowPlaying.username`: same rule.
- `getUser`/`getUsers`/user management: accounts, unchanged.

### (d) API

New routes (kima-only, D-243), DTOs in `crates/kima-api-types/src/profiles.rs`:

| Route | Who | Body → answer |
|---|---|---|
| `GET /api/profiles` | any profile | `{ profiles: [Profile], current: uuid, max: 5 }`, ordered main first, then `created_at` |

### (f) Concurrency and security

- Cross-account isolation is unchanged and remains the security boundary. **Profiles are a convenience partition, not a security boundary, until the PIN follow-up**: any profile can switch to main. The plan says so in D-240 and the README.
- Within an account, a profile never reads or writes a sibling's private data (test matrix, Task 9). Public playlists stay visible to everyone, siblings included (Q8).
- Limit and name races are decided in the DB (trigger with account row lock, unique index); Task 2 has a two-connection test.
- Deleting a profile while it has an open session: the next request with its token is 401; its SSE streams get a targeted revoke event; its app tokens are gone by cascade (Subsonic answers 44 `invalid api key` / 40); its NowPlaying slots are dropped.
- Deleting a profile while a podcast download job for it is queued: the job's `upsert_download` hits the FK → the job fails permanently with a logged reason (no retry loop) — test in Task 5. The downloaded file is shared per episode and stays for other profiles; files no row references are a pre-existing cleanup gap (account delete has it too), see Follow-ups.
